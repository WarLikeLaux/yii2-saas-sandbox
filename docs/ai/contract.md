## ⚠️ ЖЕСТКИЕ ОГРАНИЧЕНИЯ СТЕКА (СТРОГО PHP 7.4)

Проект работает на **PHP 7.4**. Тебе категорически запрещено использовать синтаксис и возможности PHP 8.0 и выше. Любое нарушение приведет к фатальной ошибке на сервере.

### 🚫 КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО использовать:
- Constructor Property Promotion (объявление свойств в конструкторе: `public function __construct(private string $x)`).
- Выражение `match`. Вместо него используй `switch` или ассоциативные массивы.
- Nullsafe-оператор (`?->`).
- Union Types (объединение типов: `string|int`).
- Readonly-свойства и readonly-классы.
- Названные аргументы при вызове функций (`foo(name: 'bar')`).
- Асимметричную видимость свойств (asymmetric visibility).
- Любые функции стандартной библиотеки, появившиеся в PHP 8.0+ (например, `str_contains`, `str_starts_with` — пиши их аналоги на `strpos`).

## 📝 СТРОГИЕ СТАНДАРТЫ PHPDOC (ОБЯЗАТЕЛЬНО НА РУССКОМ)

В SaaS приняты жесткие стандарты документирования. Каждая строка кода должна быть понятна. Любой создаваемый тобой класс, метод, свойство или константа должны быть максимально задокументированы с помощью phpDoc.

### Требования к документированию:
1. **Язык:** Все описания в phpDoc (описание классов, методов, параметров, переменных) должны быть написаны исключительно на русском языке, грамотно и технически точно.
2. **Классы:** Каждый класс обязан иметь phpDoc-блок с подробным описанием его роли в системе.
3. **Методы:** Каждый метод должен быть описан:
   - Что делает метод.
   - Описание каждого параметра через `@param` (тип, имя переменной, описание на русском).
   - Описание возвращаемого значения через `@return` (тип, описание на русском).
   - Все возможные выбрасываемые исключения через `@throws`.
4. **Свойства:** Каждое свойство класса должно быть описано через `@var` с указанием типа и назначения на русском.

### Шаблон правильного оформления кода (PHP 7.4):

```php
namespace app\services;

use Yii;
use yii\base\Component;
use yii\base\Exception;

/**
 * Класс-сервис для работы с распределенными блокировками в Redis.
 * Обеспечивает защиту от состояния гонки и дублирования обработки событий.
 */
class LockService extends Component
{
    /**
     * @var int Время жизни блокировки по умолчанию в секундах
     */
    public $defaultTtl = 10;

    /**
     * Пытается захватить распределенную блокировку для указанного ключа.
     *
     * @param string $key Уникальный ключ блокировки (например, ID события)
     * @param string $token Уникальный идентификатор воркера (UUID)
     * @param int|null $ttl Время жизни блокировки в секундах (если null, используется дефолтное)
     * @return bool Возвращает true, если блокировка успешно захвачена, иначе false
     * @throws Exception Если произошла ошибка при работе с Redis
     */
    public function acquireLock(string $key, string $token, ?int $ttl = null): bool
    {
        $expireSeconds = $ttl ?? $this->defaultTtl;
        
        $result = Yii::$app->redis->executeCommand('SET', [
            $key,
            $token,
            'EX', $expireSeconds,
            'NX'
        ]);

        return $result === 'OK';
    }
}
```

## 🛠️ АРХИТЕКТУРНЫЕ СТАНДАРТЫ SAAS (HIGH LOAD & RESILIENCE)

При написании кода всегда соблюдай следующие правила надежности:

### 1. Работа с PostgreSQL и PgBouncer:
- Мы используем PgBouncer в режиме транзакций (`Transaction Mode`). Реальные подготовленные запросы (`PREPARE`) на уровне СУБД запрещены. В конфигурациях PDO всегда должна быть включена эмуляция: `PDO::ATTR_EMULATE_PREPARES => true`.
- Все пакетные вставки (Batch Insert) должны группироваться по 500-1000 записей и обязательно оборачиваться в единую транзакцию (`db->beginTransaction()`).
- Для предотвращения дедлоков (Deadlocks) при блокировке нескольких строк всегда сортируй массив их идентификаторов по возрастанию (`sort()`) перед вызовом `FOR UPDATE`.

### 2. Очереди и фоновые задачи (RabbitMQ & yii2-queue):
- Все тяжелые операции (парсинг, отправка вебхуков, импорт истории, отправка почты) должны выноситься в фоновые задачи (`yii2-queue`).
- Задачи, работающие с внешними нестабильными API, должны реализовывать `RetryableJobInterface` для повтора при ошибках.

### 3. Интеграция с внешними API (amoCRM, Bitrix24, Авито):
- Любой HTTP-запрос (Guzzle / HTTP Client) должен иметь явные и жесткие таймауты: `connect_timeout` не более 2-3 секунд, `timeout` (read timeout) не более 10-15 секунд.
- При получении ошибки `429 Too Many Requests` извлекай заголовок `Retry-After` и отправляй задачу обратно в очередь с задержкой через метод `delay()`, вместо усыпления процесса через `sleep()`.
